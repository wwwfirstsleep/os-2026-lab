# 理解与体会

我对Shell的理解是：它负责解析命令、组织进程和连接文件描述符。输入一条命令后，需要先判断它是内部命令还是外部程序，再决定怎样执行。我认为把解析、执行和文件描述符处理分开，能更清楚地定位问题，也能把代码与操作系统原理对应起来。

我用cd来理解父子进程的区别。当前工作目录属于进程，子进程调用chdir不能修改父Shell的目录，所以普通cd必须在主进程执行。外部命令则先fork，再由子进程execvp加载程序；exec成功后替换程序映像，不会回到原来的调用点。父进程继续作为Shell存在，并用waitpid等待和回收子进程。管道里的cd只影响子进程，这与普通cd的执行位置不同。

我理解的重定向，是改变命令实际使用的输入或输出通道。0、1、2分别是标准输入、标准输出和标准错误。echo hello > out.txt通过open打开文件，再用dup2让描述符1指向它，后续输出才会写入文件。主进程执行内部命令后，还需要刷新缓冲并恢复原描述符。我特别区分了这与strace -o的用途：后者保存跟踪日志，不能证明Shell实现了I/O重定向。

管道让我关注到并发和文件描述符的生命周期。pipe提供读端和写端，分别连接右命令的输入与左命令的输出。若先等待左端结束才启动右端，大量输出可能填满缓冲区而阻塞。无用端点也必须关闭，否则读端可能等不到EOF。因此我认为，项目中的十万行数据和读端提前退出测试，比只看一条短管道的结果更有说服力。

对于环境变量，我理解PATH决定execvp如何搜索不带斜杠的外部命令；HOME用于无参cd，以及本项目支持的独立参数展开。分析strace时，我会结合PID、参数和返回值判断行为。C库接口与内核调用不一定同名，例如open可能对应openat，fork对应clone，waitpid对应wait4，不能因为名称不同就判断功能没有执行。

我认为验收应同时检查输出、退出码、文件内容和系统调用记录。开发阶段受限环境中的失败与后续GitHub成功复验属于不同运行，应分别保留。我采用Agent协助开发，并通过代码、测试与日志梳理这些原理。报告中的功能范围以实际证据为准。
